# GUI decisions

> Historical context: entries dated before the public split describe the embedded GUI prototype. This standalone app executes the installed CLI and does not import private CLI packages. Read [ARCHITECTURE.md](ARCHITECTURE.md) for the current contract; older decisions remain here to preserve their reasoning.

Decisions that shaped the GUI, and the ones still open. Each entry says what was
chosen and why, so the reasoning survives the person who had it.

Mechanics live in [`ARCHITECTURE.md`](ARCHITECTURE.md); this file is about the
choices behind them. Most entries exist because something was tried and did not
work, so an entry is usually cheaper to read than the mistake is to repeat.

**Open questions come first.** Everything under _Settled_ is decided — if one
looks wrong, raise it rather than quietly changing course, and if you do change
it, update the entry.

## Open — revisit these

### Embedded terminal for interactive commands

**Status: chosen provisionally 2026-08-14, explicitly flagged for review.**

`playroom connect` and `auth login` need a real TTY, so they are handed to the
user's terminal (Terminal.app, iTerm, Ghostty) running the same command line the
GUI would otherwise have run.

The alternative is embedding a terminal in the app — xterm.js in the frontend
with a PTY (`creack/pty`) on the Go side — so those commands run in a tab inside
the GUI. That is a materially better experience and would make the GUI
self-sufficient, but it is a feature in its own right, and Windows PTY support
is its own project.

Hand-off was taken as the cheapest correct option, not as the end state. **This
should be confirmed or replaced deliberately.**

### Root flags

`--debug` and `--request-timeout` became reachable when commands moved to
subprocess execution, and nothing uses them yet.

`--context` and `--organisation` are settled: the GUI switches the stored
config instead of passing them per command — see below.

### Concurrency

Subprocess execution makes parallel operations safe as far as process state
goes, but two concurrent writes still race on `~/.acloud.yaml`. Mutations are
not currently serialized.

**Where the fix has to live, checked 2026-09-12.** Not here. Because every
mutation is a subprocess, the racing parties are _processes_, not goroutines —
so a mutex in `App` would only stop the GUI racing itself, and would do nothing
about the user running `acloud config use-organisation` in their terminal at the
same moment. Worth having as a cheap mitigation, but it is not the fix.

The fix is in `pkg/contextmanager` in the root module. `ConfigWriter` opens the
file `O_WRONLY|O_CREATE|O_TRUNC` and writes in place, with no lock and no
temp-file-and-rename. So the failure mode is worse than a lost update: the file
is truncated to zero first, and a second process reading in that window sees an
empty config. A crash or an interleave between the truncate and the write leaves
the user with no contexts and no credentials.

Two independent changes, both root-module:

- **Write atomically** — marshal to a temp file in the same directory, then
  `os.Rename` over the original. Removes the truncation window entirely and is
  the larger win for the smaller change.
- **Take an advisory lock** for the read-modify-write, so two processes cannot
  both compute a new config from the same starting point.

Neither belongs in `gui/`, and the GUI is not the only thing exposed to it —
this is reachable from the CLI alone by scripting two commands in parallel.

## Settled

### Public GitHub checks and automated releases - 2026-09-18

GitHub now runs the standalone app's formatter, linter, frontend build and tests,
Go vet and race tests, generated-binding check, and universal macOS release
rehearsal. This closes the CI gap recorded for the embedded prototype.

The public test suite does not import the private CLI or run its former Cobra
parity tests. Argument serialization and frontend input coverage remain checked;
compatibility with the CLI still needs verification.

Release Please prepares version and changelog PRs. Merging one creates the tag
that triggers Wails packaging, GoReleaser archiving, verification, GitHub uploads
and a Homebrew cask update. Renovate proposes dependency updates without merging
them. The repository uses Apache-2.0, matching acloud-toolkit.

The app is currently ad-hoc signed. The Homebrew cask removes quarantine from
this app only; Developer ID signing and notarization remain a future step.
See [RELEASING.md](RELEASING.md) for setup and the exact release flow.

### The GUI re-reads the CLI config on every lookup — 2026-09-12

`backend/local` calls `contextmanager.Init()` before each read, behind a mutex.
It costs a small file read per lookup, and it fixed two bugs that were both
reachable on a first launch.

**The config was loaded once, at startup.** `contextmanager` keeps its state in
a package global and never looks at the file again, while every command the GUI
runs is a subprocess that writes it — organisation switches, context switches,
saved defaults — as is the user's own terminal. The `auth login` hand-off
depends entirely on noticing a change: it opens a terminal, the CLI stores a
credential, and the GUI polls `IsLoggedIn` to find out it worked. Against a
startup snapshot that poll could never return true, so a _successful_ login ran
the full two-minute timeout and then reported "Still not signed in".

**`CurrentContext()` exits the process when no context is set.** It prints to
stderr and calls `os.Exit(1)` — reasonable for a command, fatal for a desktop
app. Someone who has never run acloud has no config file, and `IsLoggedIn` is
among the first things the shell calls at startup, so the window closed
immediately with the explanation going to a stream nobody reads. `IsLoggedIn`
now checks `HasCurrentContext()` first, which is pure.

Both are pinned by tests in `backend/local/session_test.go`, which point the CLI
at a temporary file through `ACLOUDCONFIG` and never run a command.

**What is not fixed:** a _malformed_ config — one naming an api or user that is
not there — still reaches an `os.Exit` deeper inside `GetContext`. Closing that
means the CLI's config code returning errors instead of exiting, which is a
change in the root module. Library code that exits the process is the real
defect; this entry only covers the reachable half of it.

### Windows packaging removed; macOS only in the tree as well as the prose — 2026-09-12

`build/windows/` held everything Wails scaffolds for a Windows release — an
NSIS installer, an MSIX manifest, an icon and an exe manifest — and none of it
led anywhere. The terminal hand-off that `playroom connect` and `auth login`
depend on is implemented for macOS only, so a Windows build would have shipped
an app whose two interactive commands cannot run.

"macOS only, and honest about it" was already the decision. The packaging
assets quietly contradicted it: anyone opening the tree would reasonably
conclude Windows was supported and half-finished rather than not attempted.

Removed, along with its include in `Taskfile.yml` and the Windows icon step in
`build/Taskfile.yml`. The platform-guard Go files stay — `terminal_other.go`
still returns a clear "not supported on this OS yet" naming the command to run
by hand, and `launcher/interface_detach_windows.go` still compiles — so nothing
prevents the module building elsewhere. Only the claim that it ships there is
gone.

If Windows is wanted later, the hand-off is the work; `wails3` regenerates the
packaging.

### The GUI names the acloud version it was verified against — 2026-09-12

`backend/local.VerifiedAgainstAcloudVersion` records the acloud release whose
flags and defaults these screens were last checked against by hand. When the
running acloud is newer, the sidebar says so under the version number.

The reasoning is the gap above. The standalone GUI drives the installed acloud binary, so it
always runs the exact CLI it will invoke — there is no version skew in the
subprocess. What there _can_ be is skew between the CLI and the screens: bump
the release, rebuild, and a flag added in between has no control anywhere in the
UI. The parity tests exist precisely to catch that, but until they run in CI
they only catch it for whoever ran them. This is the backstop that reaches the
person actually using the app.

It is deliberately **hand-maintained, not derived from the build**. A number the
build sets would only ever say "this binary is this version", which the user can
already see. The value of this one is that a person looked at the screens
against that CLI. Raise it when you have done that, not when the release
changes.

It is deliberately **quiet in every uncertain case**. An older or equal acloud
says nothing, because the GUI was checked against something at least as new. A
version that cannot be parsed says nothing either — a development build reports
no version at all, and warning every developer working on the GUI about their
own build would train everyone to ignore it.

It is deliberately **not an error**. Commands are unaffected: they run the real
acloud, which is the whole architecture. The only thing at risk is a control
being absent, so the notice is amber, sits under the version, and never blocks
anything.

### The Defaults screen affects what the GUI creates — 2026-08-21

Two separate things had to be true for a user's `playroom config` defaults to
reach a GUI-created playroom, and for a while only one of them was.

**Commands run for real.** They used to be _detached_ cobra subcommands, so the
parent hook applying configured defaults never fired. Subprocess invocation
fixed that in the rework.

**Forms open on the configured values.** The create form filled every field from
constants compiled into the frontend, so the GUI sent an explicit value for
everything and the command had no unset flag left to default. The connect dialog
did the same with `user` and `forward-agent`. Both now seed from
`getPlayroomDefaults()` through `PlayroomDefaultsService`, with the constants
kept only as the fallback for a CLI that does not know a key.

`--read-only`, `--privileged` and `--forward-agent` are still sent explicitly —
that is deliberate and unchanged, since the GUI renders each as a definite
toggle. The difference is that the toggle now _starts_ where the user's config
says it should.

### The CLI is the only source of truth — 2026-08-14

The GUI runs real acloud commands rather than reimplementing them. See
[`ARCHITECTURE.md`](ARCHITECTURE.md) for the mechanism.

The alternative — calling the same Go packages the commands call — was what the
GUI did before, and it drifted invisibly: because it executed _detached_ cobra
subcommands, the parent hook that applies `playroom config` defaults never ran,
so the GUI's own Defaults screen had no effect on the playrooms it created.
Nothing in the code said so. Running the real command makes that class of bug
structurally impossible.

### Status may refresh directly; listings may not — 2026-08-21

An amendment to the rule above, because the original wording forbade something
worth allowing. It said anything _a CLI command already covers_ must go through
the CLI — and a playroom's status is covered by `playroom list`, so keeping a
red/green indicator current meant re-running that whole command on a timer.

That is the wrong price for the job. A subprocess spawn, cobra init, platform
API auth, a kubeconfig load and a JSON round trip, every second, to recolour a
dot.

So the line moved, and it is no longer read-versus-write. It is **what exists**
versus **how a known thing is doing right now**. The CLI owns the first
absolutely — which playrooms are there, how they are configured, who owns them.
The second may take a direct path once the CLI has already established the row.

The test, when it is not obvious: _could this call, on its own, make the GUI show
a playroom that is not there, or hide one that is?_ If yes, it is a listing, and
it belongs behind the CLI.

Two conditions keep this from becoming the hole that swallows the rule. A direct
status refresh calls **the same `pkg` function the command calls** — the same
code with the subprocess hop removed, never a second query written for the GUI —
so the two cannot disagree about what a status means. And it **never wins an
argument**: the CLI's answer is the truth, and the next CLI read overwrites
whatever the fast path put on screen.

Mutations are untouched by any of this. Create, delete, start, stop, update,
config writes and scope switches are real commands, always.

See [`ARCHITECTURE.md`](ARCHITECTURE.md) for the same rule next
to the code it governs.

### There is no Retry, because there is no `playroom retry` — 2026-08-21

Failed playrooms used to show a Retry button on the card and the detail screen.
It ran nothing: it set the row to "creating" and raised a toast, and the next
poll put it straight back to failed.

It was not wired up because there is nothing to wire it to. A retry means delete
then create, and the CLI has no single command for that — so building one in the
GUI would be the GUI inventing behaviour the CLI does not have, which is the one
thing this design exists to prevent.

Failed rooms now offer **Edit**, which is a real command (`playroom update`) and
usually the actual fix: the image or the resource requests are wrong. Delete is
the other honest answer.

If a first-class retry is wanted, it belongs in the CLI as `playroom recreate`,
and the GUI would then call it like anything else.

### Commands run as a subprocess of ourselves — 2026-08-14

`os.Executable()`, not a PATH lookup for `acloud`. The GUI ships inside the
acloud binary, so the running executable is exactly the right CLI — same build,
no version skew, and it works for a user who only ever launches the app from
Finder.

### Output is captured always, shown on request — 2026-08-14 (revised)

`playhouse create` runs for around twenty minutes. The GUI used to show nothing
at all for the whole of it, and a failure surfaced as a bare `exit status 1`
with the CLI's own explanation discarded. Every command's real stdout and stderr
is now captured, with the exact arguments.

The first version put that output permanently on screen. Tried against a live
playhouse, it was too loud: creating a playroom is a background job, and the
user wanted the plain "Created" toast back, not a wall of CLI output every time.

So the toast and the room's own state are the signal, and the output goes to an
**activity log** that stays closed until asked for — from the sidebar, or by
clicking the toast that started it. The log is one continuous terminal-style
scrollback of everything run this session, held in memory and gone when the app
closes; a scrollback you can read top to bottom beat a structured list of runs
on both familiarity and effort.

**A failure opens the log by itself**, at the command that failed. Quiet is the
right default while things work; the moment they don't, the output is the entire
reason it was captured.

Polled reads are never logged. They run without an operation id, so they emit
nothing — otherwise a list refreshing every ten seconds would bury everything
worth reading.

### Displayed commands are redacted — 2026-08-14

`playhouse create` takes a Tailscale OAuth secret on its command line, and the
GUI shows commands verbatim. So the credential a user had just typed was printed
back to them and copied to their clipboard with the rest of the command.

`cli.Preview` now redacts any flag whose name contains `secret`, `token`,
`password` or `passwd` — matched by substring, so a credential flag added to the
CLI later is hidden by default rather than leaking until someone remembers.
Redaction applies only to what is shown: previews, the log, and error messages.
The executed command keeps the real value.

This is the one place the displayed command deliberately differs from the one
that runs.

### The GUI replaces fzf pickers, not the commands behind them — 2026-08-14

`config use-organisation` and `config use-context` show an fzf picker when run
in a terminal, which looked at first like something the GUI could not do.

It isn't. fzf is only how those commands _obtain an argument_: both take the
value directly (`cobra.RangeArgs(0, 1)`), and the picker is reached only when no
argument was given **and** stdout is a TTY. So the GUI renders the list and
passes the choice — `acloud config use-organisation avisi` — and the picker
never enters into it.

It also degrades safely rather than hanging: in a subprocess stdout is not a
TTY, so a no-argument call returns `invalid organisation` instead of waiting on
an fzf that will never appear.

The same applies to every other fzf-backed command (`kubeconfig get/install`,
`shell`) if they are ever wanted in the GUI. **Render the selection; pass the
result as an argument.**

### Switching organisation writes to the user's config — 2026-08-14

The GUI runs `config use-organisation <slug>`, which updates `~/.acloud.yaml`.
So switching in the GUI switches the user's terminal too.

The alternative was carrying `--organisation` on every command the GUI runs,
leaving the config untouched. That was rejected because it lets the GUI and the
shell drift into different organisations without saying so — and because
"do what the command does" is the rule the rest of this GUI follows.

Switching invalidates almost everything on screen: playhouses, playrooms and the
cached playhouse all belong to the organisation being left. The shell clears
that state and returns to playhouse selection rather than leaving a stale list
up.

### Dangerous flags are exposed, not hidden — 2026-08-14

`--privileged` (all Linux capabilities, host device access) and `--force`
(bypasses the owner guard) are available from the GUI, behind an Advanced
section with the CLI's own warning text, and `--privileged` additionally
requires an acknowledgement.

A GUI that quietly omits flags stops being a mirror of the CLI, and users end up
distrusting it. Better to show the flag and the warning.

### macOS only, and honest about it — 2026-08-14

Terminal hand-off is implemented for macOS. Other platforms return a clear
"not supported on this OS yet" error naming the command to run by hand, rather
than failing silently. Windows packaging exists in `desktop/build/windows` but
the hand-off is not implemented for it.

### Previews are generated by the backend — 2026-08-14

The preview and the executed command come from one value, so they cannot
disagree. The previous TypeScript builders already had.

### `play` is not in the GUI — 2026-08-22

Play has now been taken out twice, for different reasons, and the second reason
is the one worth remembering.

The first removal, on 2026-07-02, was about behaviour: a drawer-based flow that
reused saved playroom defaults kept surfacing rough edges, such as an invalid
memory-request-above-limit default that only failed at launch.

It came back on 2026-08-14 as a terminal hand-off, which fixed that — the CLI
kept ownership of the session and its defaults, and the GUI only chose where to
open it. The dialog was built and wired end to end. What never landed was a way
in: the button and the `p` shortcut that opened it were dropped, and nothing
replaced them. It then sat unreachable in a shipping build, with the
flag-coverage test reporting all fifteen of its fields as wired — because they
were. Both guard tests were green and neither could see the problem.

So it is out again, this time because dead UI in a release is worse than a
missing feature. `acloud playroom play` is unaffected and remains the way to do
this.

**If it returns, the entry point comes first.** A hand-off is still the right
shape; do not rebuild the old drawer flow.

### The CLI reference is generated — 2026-08-14

`make docs` produces the full flag reference for every command from the cobra
tree. The hand-maintained 41 KB copy that used to live in `gui/` was deleted: it
documented a `gui_function.go` that no longer existed and had signatures that
were simply wrong.

Documentation here describes structure and decisions — things a generator cannot
produce. Flags are never listed by hand.

## GUI module and launch command - 2026-09-11

The desktop application now launches with `acloud playhouse interface`.
The old `playroom interface` command is removed. A CLI-only build reports how
to obtain the GUI; `make gui-dev` starts development from the repository.

`gui/` owns a separate Go module, the launcher, and its build recipes. Its main
package compiles the CLI together with Wails for both development and release,
so subprocesses still execute exactly the same CLI build. The root CLI module
never imports the GUI. This replaces the earlier root `cmd` registration under
a build tag and makes removing `gui/` independent of CLI builds and module
maintenance. GUI builds no longer run `go mod tidy` implicitly.
